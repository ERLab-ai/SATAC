# Release integrity candidate

## Policy and defect
Reopened docs/editorial/knowledge-publication-policy-v1.2-ar.md and db/migrations/0001_knowledge.sql. A valid correction must be versioned, auditable and not affect unrelated public data. The old correct() passed the entire active membership to publish(), which projected every version again from mutable staging evidence, geometry and temporal records. This could silently change an unrelated public payload under the same version ID.

## Migration 0012
The public payload is authoritative once a version is published. publish() uses the active release's stored payload for an existing member, else the latest stored historical payload for a previously published version, else project() for first publication. Member order is canonical by UUID as before; hash and member insertion share one materialized snapshot. Existing releases are not rewritten. Version lookup index added. Staged successors do not implicitly replace active members. Newly admitting a superseded version is rejected; carrying forward an active version with an unrelated staged successor is allowed (draft is not publication authorization). Existing synthetic/restricted/known-incorrect/withdrawal checks remain. correct() retains its existing validation, advisory lock, transactional audit, old withdrawal and internal task handling. Unchanged records carry forward through the same protected publish() path. A late reference, date or geometry improvement must use a successor version for public publication rather than modify an already released payload.

Internal verify_release(uuid) checks the stored manifest against ordered stored members, returns null for an unknown release, accessible only to publisher/curator and owner. The live withdrawal overlay is intentionally not hashed as the original stored release. No public audit endpoint. Existing historical releases may have had different projections of the same version under earlier migrations; migration chooses active, otherwise latest stored historical payload and does not retroactively reconcile them. No cross-PostgreSQL-version canonical digest guarantee.

## Remaining limitations
Trusted staging owner may edit dependent staging rows; this does not alter previously published payloads. Dynamic restriction/revocation of a previously exposed source or geometry needs a separate public suppression mechanism; immutable stored payload reuse does not implement one. Explicit successor publication workflow for non-error enrichment, rollback selection policy, concurrent staging/publish stress tests, historical payload divergence audit, cross-version canonical hashes, authenticated service deployment and operational recovery remain pending. No production release or merge.
